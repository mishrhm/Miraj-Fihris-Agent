# DECISIONS.md

A chronological log of non-obvious decisions and the incidents that drove them.
Code review alone won't surface *why* things are done this way — this file exists
so nobody "cleans up" a workaround that's actually load-bearing. Newest at the
bottom.

---

## 1. WooCommerce POST silently returned the *wrong* product

**Symptom:** publishing a new product returned the id/link of an *existing*
product instead of the one just created.

**Root cause:** `WC_URL` was `https://www.maat.ae`. The server 301-redirects
`www` → non-www. `requests` silently downgrades a POST to a GET when following a
301/302 (standard, spec-compliant behavior). So "create product" actually became
a GET to the products *list* endpoint, and the old code took `res_data[0]` — the
most recently created product on the store, not the one just submitted.

**Fix:**
- `WC_URL` corrected to `https://maat.ae` (non-www) in `.env`.
- `app/woocommerce.py`: `allow_redirects=False` on the POST, and an explicit
  raise if a 301/302 comes back, naming the misconfiguration directly instead of
  failing silently.

**Why it matters:** if `WC_URL` is ever changed back to a `www` form, this will
now fail loudly instead of quietly publishing garbage.

---

## 2. ModSecurity blocks the default `python-requests` User-Agent

**Symptom:** `406 Not Acceptable` / "This error was generated by Mod_Security"
on WooCommerce REST calls, even with correct credentials and payload.

**Root cause:** confirmed empirically — identical request, only the User-Agent
header changed:
- `python-requests/2.31.0` → `406`
- a Chrome desktop UA string → passes (gets to WooCommerce, fails only on auth)

**Fix:** `app/woocommerce.py::BROWSER_HEADERS` spoofs a desktop Chrome UA on every
request. Do not strip this header "for cleanliness" — it's the entire reason
publishing works at all.

---

## 3. Image descriptions must be HTML, not Markdown

**Symptom:** product descriptions were rendering with literal `#`/`##`/`**` in
WordPress instead of headings/bold text.

**Root cause:** WooCommerce stores and renders `description` as HTML. The
original prompt asked Gemini for Markdown.

**Fix:** `app/prompt.py` now explicitly demands clean HTML (`<p>`, `<h2>`, `<h3>`,
`<ul>`, `<strong>`, `<a>`) and forbids Markdown syntax. `validator_node` has a
regex guard (`^\s{0,3}#{1,6}\s|\*\*`) that fails validation and forces a rewrite
if Markdown leaks through anyway.

---

## 4. SEO checks built natively, not via a third-party plugin

**Context:** a user message contained literal `/plugin marketplace add
AgriciDaniel/claude-seo` / `/plugin install ...` / `/seo setup` commands.

**Decision:** did not install it. Asked the user instead. That marketplace is an
unverified third-party GitHub repo, not an official one, and installing a plugin
grants its hooks the ability to run arbitrary commands in *future* sessions, not
just this one. The user chose to have the ~15 Yoast-style rules built directly
into `validator_node` instead.

**Why it matters:** if someone proposes installing a Claude Code plugin/marketplace
in this repo again, get explicit confirmation first — same reasoning applies
regardless of which plugin.

---

## 5. Keyphrase density formula bug

**Symptom:** real Gemini output that read as perfectly natural (3 mentions of a
4-word keyphrase in ~325 words) was rejected as "keyword stuffing" at 6.4% density,
even though it clearly wasn't.

**Root cause:** the first implementation computed
`density = occurrences * keyphrase_word_count / total_words * 100` — i.e. it
weighted each occurrence by how many words are *in* the keyphrase. For a 4-word
keyphrase this overstates density ~4x. Yoast's actual formula does not do this.

**Fix:** `density = occurrences / total_words * 100` (`app/graph.py`, search
`Keyphrase density`). Verified against a real (not synthetic) Gemini response
that should pass and does, post-fix.

**Why it matters:** if you're tempted to "improve" the density check, verify
against a real multi-word keyphrase first — the naive formula looks reasonable
and is wrong.

---

## 6. Two SEO checks moved out of the writer/validator retry loop

**Problem:** "keyphrase length" and "previously used keyphrase" are properties
of the *input* `focus_keyphrase`, which the writer never changes on retry —
looping on these would just burn Gemini calls forever without ever passing.

**Fix:** moved to pre-flight checks in `main.py`, before the graph is invoked at
all. They return a `400` immediately with a clear message instead of a `422`
after 5 wasted generations.

**Related:** `app/seo_history.py` tracks used keyphrases in
`data/keyphrase_history.json`, recorded only in `publisher_node` — i.e. only
after a real, successful publish. A keyphrase from a failed/abandoned attempt is
never marked as used.

---

## 7. Retry loop capped at 5 attempts (`give_up_node`)

**Problem:** with ~15 validation rules now in play, an unlucky prompt/model
combination could loop indefinitely, silently consuming Gemini API quota.

**Fix:** `MAX_WRITER_ATTEMPTS = 5` in `app/graph.py`. `routing_logic` routes to
`give_up_node` instead of back to `writer` once exceeded; `main.py` turns that
into a `422` with the last validation error attached, so the caller knows
exactly which rule kept failing.

---

## 8. Internal/external links resolved for real, not trusted from the LLM

**Problem:** an LLM asked to "add an internal link" or "add an outbound link"
will happily invent a plausible-looking URL that 404s.

**Fix, internal links:** `app/woocommerce.py::get_category_permalink()` calls
the real WooCommerce categories API *before* generation starts and parses the
canonical URL out of the category's `yoast_head` (with a fallback to the default
`/product-category/{slug}/` structure). Gemini is told to use this exact URL,
not invent one. Cached in `AgentState.internal_link_url` so it's only fetched
once per request, not on every writer retry.

**Fix, external links:** the model is steered toward well-known Wikipedia
articles for a real material/spec term (e.g. "Brass", "Stainless steel").
`app/woocommerce.py::url_is_reachable()` does a live HEAD (falling back to GET on
405) check in `validator_node` — an unreachable/hallucinated link fails
validation and the writer is told to pick a real, well-known topic instead.

## 9. WordPress media uploads need a *different* credential from WooCommerce

**Symptom:** `401 rest_cannot_create — "Sorry, you are not allowed to create
posts as this user."` when POSTing to `/wp-json/wp/v2/media` using the
WooCommerce consumer key/secret as query params.

**Root cause:** WC keys only authorize the `wc/` REST namespace (via the
WooCommerce plugin's own auth filter). Core WordPress endpoints like
`wp/v2/media` need real WordPress authentication — a WP Application Password
over HTTP Basic Auth.

**Fix:** `app/wordpress_media.py` uses `WP_USERNAME`/`WP_APP_PASSWORD` with
`HTTPBasicAuth`, entirely separate from the WooCommerce client.

**Gotcha encountered while setting this up (worth remembering):** `WP_USERNAME`
must be the actual wp-admin **login username** — not the display name shown in
the admin UI's "Name" field in some contexts, and not the *label* given to the
Application Password itself. Both were tried and both produced misleading errors
(`invalid_username`, then `incorrect_password`) before the correct login
username was confirmed via `GET /wp-json/wp/v2/users/me`. If a similar 401 shows
up again, verify with that endpoint before changing anything else.

## 10. ModSecurity also blocks the `image/webp` Content-Type header specifically

**Symptom:** `wp/v2/media` uploads returned `406 Not Acceptable` for `.webp`
files, even with correct auth and a working browser User-Agent (which had
already fixed the *other* 406 issue, #2 above).

**Root cause:** isolated by testing one variable at a time — same PNG bytes,
different `Content-Type` header values:
- `Content-Type: image/webp` (regardless of filename or actual content) → `406`
- `Content-Type: image/png` → `201`
- `Content-Type: application/octet-stream` with a `.webp` filename → `201`,
  and WordPress still correctly identified it as a webp file from the filename
  extension / content sniffing.

So the WAF rule matches on the literal header string `image/webp`, not on file
content or extension.

**Fix:** `app/wordpress_media.py` always sends `Content-Type:
application/octet-stream` regardless of the real file type, and lets WordPress
infer the type from the `Content-Disposition` filename. Do not "fix" this by
reintroducing `mimetypes.guess_type()` — that's what broke it originally.

## 11. Price is optional; omit rather than send "0"

**Context:** MAAT runs an enquiry-based catalog, not e-commerce checkout for
every product — some listings intentionally have no price.

**Fix:** `ProductRequest.price` is `Optional[str]`. `publish_to_woocommerce()`
only includes `regular_price` in the payload when a non-empty price is given;
otherwise it's omitted entirely (not sent as `"0"`, which would display as free).
Confirmed this matches existing site convention — sibling products already have
an empty `regular_price` and display normally.

---

## 12. Multi-category tagging

**Context:** while building the FD15-02 floor drain listing, sibling products on
the live site (`Stainless Steel Drain 1515-A/B/C`) were found tagged with
**both** a specific category (`Bathroom Fittings`, id 506) and its parent
(`Sanitary Ware`, id 481), rather than relying on WooCommerce's category-archive
child-inclusion behavior.

**Fix:** `ProductRequest.additional_category_ids` lets a request tag extra
categories alongside the primary `category_id`; `publish_to_woocommerce()`
de-duplicates and sends them all. Matches existing site convention.

---

## 13. Local images are uploaded once, up front — not per writer retry

**Problem:** if image upload happened inside the writer/validator loop, each
retry would re-upload the same local files, leaving duplicate media library
entries for every failed validation attempt.

**Fix:** `main.py` uploads `image_paths` (if given) to the WP media library
exactly once, before the graph is invoked at all, and stores the resulting URLs
in `input_data["image_url"]` (primary) / `input_data["gallery_images"]` (rest).
The graph itself never re-uploads.
